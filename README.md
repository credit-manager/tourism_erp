# Tourism ERP — نموذج أولي (Prototype)

نظام إدارة شركة سياحة وسفر، يعمل محلياً على الكمبيوتر عبر المتصفح (شبيه بـ Odoo).

## مميزات إدارية جديدة

### 1. صلاحيات دقيقة لكل مستخدم (فوق الأدوار الثابتة)
من "الإعدادات" → بجانب كل مستخدم زرار "صلاحيات دقيقة" يفتح صفحة فيها كل صلاحية في النظام مع checkbox.
ممكن تمنح مستخدم معيّن صلاحية إضافية فوق دوره، أو تسحب منه صلاحية كانت متاحة لدوره أصلاً — بدون التأثير على باقي زملائه في نفس الدور.

### 2. سجل تتبع العمليات (Audit Log)
كل إضافة/تعديل/حذف في أي جدول بالنظام (حجوزات، عملاء، خزنة، مستخدمين... كل شيء) يُسجَّل تلقائياً باسم المستخدم الذي قام بالعملية، تاريخها ووقتها، ووصف مختصر للسجل المتأثر.
الصفحة: "الإعدادات" → "عرض سجل تتبع كل العمليات" (تظهر فقط للمدير).

### 3. واجهة ثنائية اللغة (عربي/إنجليزي)
زرار EN | AR في أعلى يمين كل صفحة. التبديل يغيّر اتجاه الصفحة (RTL/LTR) ونصوص القائمة الجانبية والعناصر الأساسية فوراً.
**ملاحظة:** التغطية الحالية تشمل التنقل والعناصر المشتركة؛ ترجمة كل حقول كل نموذج في كل موديول هي امتداد طبيعي للنظام الحالي عبر دالة `t()`.

### 4. دعم عملات متعددة
من "الإعدادات" تقدر تضيف عملات جديدة (USD, SAR, AED...) وتحدد سعر صرفها مقابل العملة الأساسية، وتغيّر العملة الأساسية في أي وقت.
كل حساب خزنة مرتبط بعملة معينة ويظهر رمزها على الرصيد.
**ملاحظة:** هذا الأساس المُطبَّق حالياً على الخزنة؛ ربط العملة بالحجوزات والتقارير والتحويل التلقائي بينها هو الخطوة التالية المنطقية.

## موديول الحجوزات الكامل (تحديث جوهري)

كل الحقول مرتبة بالضبط كما طُلب، مع حسابات تلقائية بالكامل:

رقم الحجز (تلقائي) → تاريخ الحجز (تلقائي) → تاريخ الوصول/المغادرة → **عدد الليالي (تلقائي)** → اسم العميل
→ عدد البالغين/الأطفال وأعمارهم → الجنسية → الفندق ونوع الغرفة ونوع الإقامة → عدد الغرف
→ **عدد أيام الإقامة = غرف × ليالي (تلقائي)** → سعر البيع ← التحصيل ← **المتبقي (تلقائي)**
→ سعر التكلفة ← المدفوع ← **المتبقي (تلقائي)** → **الإجمالي المبدئي = بيع - تكلفة (تلقائي)**
→ الانتقالات وخدمات أخرى → **إجمالي الربح = الإجمالي المبدئي - الانتقالات (تلقائي)**
→ **وكيل السفر** (نسبة % أو رقم ثابت من إجمالي الربح) → **مسؤول المبيعات** (نسبة/ثابت) → **مسؤول الحجز** (نسبة/ثابت)
— وكل عمولة من الثلاثة تُحسب وتُحفظ تلقائياً عند الحفظ.

**الحجز المسدد بالكامل (تحصيل = سعر البيع) يختفي تلقائياً من القائمة الافتراضية**، وتقدر تشوفه من فلتر "مسددة بالكامل" أو "الكل".

### فلتر وبحث متقدم
فلتر بالفندق، حالة السداد، تاريخ الوصول/المغادرة (من-إلى)، + **خانة بحث شامل واحدة** تبحث في رقم الحجز، اسم العميل، الفندق، الهاتف، الجواز، الجنسية، ونوع الغرفة في نفس الوقت.

## التحصيل المرحلي (توزيع دفعة على أكثر من حجز)

من "التحصيل المرحلي" تقدر تسجّل دفعة واحدة (برقم تلقائي `COL-2026-0001`) وتوزّعها على أكتر من حجز دفعة واحدة:
مثال فعلي مُختبَر: تحصيل 1000 على 3 حجوزات بمتبقي 250 لكل واحدة → يتسدد الثلاثة بالكامل (750)، والـ 250 الباقية تُحفظ "تحت الحساب" لحين التأكد من الشركة، وبعدين تقدر توزّعها على أي حجز تحب (نفس الحجز أو حجز جديد) من نفس الصفحة.
كل التحصيل بيدخل الخزنة الرئيسية فوراً كوارد بمجرد استلامه، بصرف النظر عن توزيعه.

## الشجرة المحاسبية والميزانية

- **الشجرة المحاسبية** (`/accounting/chart`): أصول، خصوم، حقوق ملكية، إيرادات، مصروفات — جاهزة بحسابات افتراضية، وتقدر تضيف حسابات فرعية جديدة تحت أي تصنيف.
- **الميزانية** (`/accounting/balance-sheet`): تُحسب لحظياً: الأصول = الخزنة + ذمم العملاء (المتبقي تحصيله من كل الحجوزات)، الخصوم = ذمم الموردين (المستحق لكل الفنادق/الموردين)، وحقوق الملكية = الفرق بينهما.
- **الأرباح والخسائر**: موجودة في صفحة "التقارير" الموجودة بالفعل (فلتر تاريخ + تصدير Excel/PDF).

**ملاحظة بالشفافية:** هذا نظام محاسبي مبسّط (Single-entry) مبني على بيانات النظام الفعلية لحظياً، وليس دفتر يومية مزدوج القيد (Double-entry Ledger) كامل. لو احتجت دقة محاسبية بمعايير المحاسبين القانونيين بالكامل، الخطوة التالية الطبيعية هي بناء قيود يومية فعلية لكل عملية.

## الخزنة وسحب الموظفين (بقاعدة الـ 50%)

صفحة "سحب الموظفين" بتورّي كل موظف: **كام حصّل** الشهر ده (من أي دور: مسؤول حجز/وكيل سفر/مسؤول مبيعات)، **كام سحب** فعلاً، والمتاح له دلوقتي.

**القاعدة المطبَّقة فعلياً ومُختبرة:**
- قبل يوم 15 من الشهر: أقصى مسموح بسحبه = **50%** من إجمالي ما حصّله هذا الشهر، ولو حاول يسحب أكتر، السيستم يرفض الطلب برسالة توضح المبلغ المسموح والمسحوب فعلاً.
- بعد يوم 15: يقدر يسحب المتبقي بالكامل (100%).

كل سحب (راتب أو سحب على الحساب) يخصم تلقائياً من حساب الخزنة المختار، وحذف عملية سحب يرجّع المبلغ للخزنة تلقائياً.
صفحة "الرواتب الشهرية" بقت تعرض كمان "المسحوب فعلاً" و"الصافي المتبقي" لكل موظف، فمربوطة بالكامل مع الخزنة.

## تسجيل الدخول
عند أول تشغيل يتم إنشاء مستخدم مدير افتراضي تلقائياً:
```
اسم المستخدم: admin
كلمة المرور: admin123
```
**مهم: غيّر كلمة المرور وأنشئ مستخدمين حقيقيين من صفحة "الإعدادات والصلاحيات" بعد أول دخول.**

## نظام الصلاحيات (3 أدوار)
- **مدير النظام (admin):** صلاحية كاملة على كل شيء (إضافة/تعديل/حذف/رواتب/إعدادات).
- **محاسب (accountant):** الخزنة، المصروفات، الموردين، عرض الموظفين والرواتب فقط (بدون تعديل/حذف موظفين أو حجوزات).
- **موظف حجوزات (reservations):** إضافة وتعديل الحجوزات والعملاء، بدون حذف، وبدون الوصول للخزنة أو الرواتب أو إدارة الموظفين.

كل مستخدم بيتسجل دخوله بكلمة مرور خاصة به، والقائمة الجانبية بتتغير تلقائياً حسب صلاحياته.

## التشغيل

```bash
pip install -r requirements.txt
uvicorn main:app --reload
```

ثم افتح المتصفح على:
```
http://127.0.0.1:8000
```

قاعدة البيانات (SQLite) تُنشأ تلقائياً في ملف `tourism_erp.db` بنفس المجلد عند أول تشغيل.

## الموديلات المتوفرة حالياً
- لوحة التحكم (Dashboard): إيرادات، مصروفات، صافي ربح، عدد حجوزات، رصيد الخزينة.
- الحجوزات: إنشاء حجز يربط (عميل + موظف + منفّذ) ويحسب تلقائياً:
  - عمولة الشركة = السعر الإجمالي - تكلفة المنفّذ.
  - عمولة الموظف = عمولة الشركة × نسبة عمولته.
  - يحدّث رصيد المنفّذ (المستحق له) ورصيد الخزنة الرئيسية تلقائياً.
- العملاء (B2C / B2B).
- المنفذين/الفنادق/الموردين.
- الموظفين (الراتب ونسبة العمولة).
- الخزنة: حسابات متعددة (رئيسية وفرعية) + سجل الحركات + إضافة حركة يدوية.
- المصروفات: تُخصم تلقائياً من الخزنة الرئيسية.

## الخطوات التالية المقترحة (المرحلة الثانية)
1. إضافة موديول الفنادق التفصيلي (الغرف، التواريخ، الحجز الآجل).
2. صفحة "كشف حساب" لكل عميل/مورد على حدة (Statement of Account).
3. تقارير قابلة للتصدير PDF/Excel (ربح وخسارة، الخزنة الشهرية).
4. صلاحيات مستخدمين (تسجيل دخول/أدوار: محاسب، موظف حجوزات، مدير).
5. تغليف التطبيق كبرنامج Desktop حقيقي باستخدام `pywebview` (بدون الحاجة لفتح متصفح يدوياً).
6. الانتقال من SQLite إلى PostgreSQL عند الحاجة لتعدد المستخدمين على الشبكة.
